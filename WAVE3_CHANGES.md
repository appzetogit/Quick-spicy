## #028a — Cancelled Order Back Navigation — **FIXED (both halves)**

### (a) The false COD refund promise

`Orders.jsx` showed **"Refund will be processed in 24-48 hours"** on any cancelled
order that wasn't wallet-paid — including cash on delivery, where the customer never
paid anything. It promised money back that was never taken.

**Root cause.** The only branch was `order.paymentMethod === 'wallet'`; everything
else fell through to the refund copy. It also read `order.paymentMethod` while the
backend stores `order.payment.method` (the flat field is a transform added at
`Orders.jsx:333`), so the wallet branch itself was unreliable.

**Fix.** A `refundNote` computed per order, checking method **and** capture status:

| Payment | Note shown |
|---|---|
| Cash / COD | **none** — nothing was ever paid |
| Wallet | "Refunded to your wallet automatically" |
| Online, `payment.status === 'completed'` | "Refund will be processed in 24-48 hours" |
| Online, pending or failed | **none** — no money was taken |

Reads both `order.payment.method` and the flat `order.paymentMethod`, lowercased, so
it works regardless of which shape the order arrived in.

No copy was invented for the COD case — the requirement says don't show the refund
message, so nothing renders. Say the word if you'd rather show
"No payment was made" for clarity.

**Already correct, left alone:** `OrderTracking.jsx:837` already branches on
cash/cod for consumer-initiated cancellation.

### (b) Back from the Order Cancelled screen

The "Order Cancelled screen" is `OrderTracking` in its cancelled state. Its back
button was a hardcoded `<Link to="/user/orders">`.

**Fix.** Back now goes to **Home** when the order is cancelled, and continues to the
orders list for live orders. A cancelled order is a dead end — there is nothing left
to track.

### Honest note on the reported symptom
The ticket says back went to **Profile**. I could not reproduce that from the code:
the in-app button went to `/user/orders`, and everything else in the module uses
`safeBack` (which falls back to Home). The Profile landing was most likely the
*hardware* back key popping browser history, which is the same root issue as #019.

What I changed implements the stated **expected** behaviour — back goes Home. If QA
still sees Profile after this, it is the hardware back key and belongs with #019 in
the Flutter shell.

## #021 — Banner Navigation to Store — **FIXED (the real cause was Back Office)**

**The consumer carousel was never broken.** `OfferBannerCarousel.jsx:68` already
navigated correctly and has since it was written. It early-returns when `linkUrl` is
empty:

```js
const link = String(banner?.linkUrl || "").trim()
if (!link) return // decorative banner
```

**The actual cause: banners were being published with `linkUrl` blank.** The whole
chain existed — the `OfferBanner` model stores it, the API returns it, the Back
Office had a field for it — but that field was a free-text box labelled
"On tap, open (optional)" with a `/user/offers` placeholder. Whoever uploads banners
had to know and hand-type the exact in-app path of the store they were advertising.
Predictably, it was left blank, and every banner shipped non-clickable.

### Fix — Back Office (`LandingPageManagement.jsx`)
Added a **store picker** above the link field. Choosing a restaurant fills in the
correct `/user/restaurants/<slug>` path automatically. The free-text field stays for
non-store destinations (`/user/offers`, external URLs).

`allRestaurants` was already loaded on that page, so this needed no new API call.
Restaurants without a slug are filtered out. Slugs are auto-generated by the
`Restaurant` model, so this should cover everything.

### Fix — Consumer (`OfferBannerCarousel.jsx`)
Banner links are authored in the Back Office, so they are untrusted input reaching
the router. Added a guard rejecting protocol-relative (`//host`) and scheme-prefixed
(`/javascript:`) values before `navigate()`. External `http(s)` links keep their
existing `window.open(..., "noopener,noreferrer")` path.

### To verify
- Create an offer banner, pick a store, save → tapping it opens that store.
- An existing banner with a blank link stays non-clickable and un-styled as clickable
  (`cursor-pointer` is already conditional). **Existing banners will need re-editing
  in BO to become clickable** — this fix does not backfill them.

### Still open — worth its own ticket
A raw path string still rots silently if a store's slug changes or the store is
deleted. A structured target (`{ type: 'store', storeId }`) resolved at read time
would be sturdier. Out of scope here.

## #020 — Banner Overlapping Address — **PARTIALLY FIXED — needs a visual pass**

**Root cause — confirmed.** On mobile the address block (`PageNavbar`) renders
*inside* the hero shell at `z-30`/`z-50`, directly over the full-bleed banner image
(`absolute inset-0`). Whether a customer could read their own address depended
entirely on whichever banner artwork was showing — dark or busy images made it
unreadable and hard to tap.

**What I changed.** The mobile header strip now paints its own opaque background
(`bg-white dark:bg-[#0a0a0a]`), so the banner image starts *below* the address
instead of running underneath it.

### Why this is marked partial — please read
This is a **one-line layout change, and I could not verify it visually.** It is the
smallest change that makes the address legible, and it is trivially revertible. But:

- The hero is a deliberate full-bleed design (`aspect-[16/9]`, `md:-mt-40`). Painting
  an opaque strip across its top **will change how the home screen looks.** Someone
  needs to actually look at it.
- The sheet says *"Complete implementation is required"*, which reads like a proper
  structural rework — moving the address out of the hero entirely — rather than a
  background fill. That is a bigger change and should follow an approved design.
- Not tested on small viewports, notched devices, or with a long wrapping address —
  which is exactly where overlap bugs originate.

**My recommendation:** treat this as a stopgap that fixes legibility now, and raise
the structural rework with design. If the opaque strip looks wrong, revert the single
class change on `Home.jsx:2303` — nothing else depends on it.
